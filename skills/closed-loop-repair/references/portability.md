# 跨代理使用

## 通用入口：无需特定安装目录

下载仓库并保持 `skills/closed-loop-repair/` 的目录结构，让代理能够读取整个文件夹。直接发送以下提示，替换成本机真实路径：

```text
请读取 <本机路径>/closed-loop-repair/SKILL.md，按需读取它引用的 references。
将其作为本次任务的工作流指导，并遵守你所在平台的指令优先级与项目规则。
检查 <项目路径> 的 <具体异常>：先判断源数据还是代码、配置或环境问题，
给出证据、具体原因、修复方案和预期效果；我确认后再修改。
验证不通过就在确认范围内返工，通过后将候选交给我验收。
先检查你是否具备读取、编辑、执行和查看结果的能力；没有的能力不要假装完成。
```

这条路径不依赖 `$skill-name`、`/skills`、MCP 或特定模型。宿主必须允许读取这些文件；只粘贴入口正文而不提供引用文件，不构成完整加载。

## Codex

原生 skill 使用：把完整 `closed-loop-repair` 文件夹放到项目支持的技能目录，如 `.agents/skills/`，或使用当前版本的 skill 安装工具。然后显式调用 `$closed-loop-repair`。不使用安装工具也可按通用入口让代理读取本地目录。

宿主显示信息位于 `agents/openai.yaml`，不包含流程逻辑。官方技能说明：<https://developers.openai.com/codex/skills/>。

## WorkBuddy、DeepSeek 驱动的桌面代理及其他工具

模型名称不等于客户端的 skill 格式。WorkBuddy、DeepSeek 模型及使用 DeepSeek 的第三方客户端不能视为同一种安装方式。

先使用上面的通用文件读取方式；如果所用客户端明确提供本地 skill 导入功能，并支持 `SKILL.md`，再将完整文件夹按该版本的导入要求安装。不要猜测或创建隐藏配置目录，不宣称 ZIP 可以被任意客户端原生导入。

当前仓库未在 WorkBuddy/DeepSeek 客户端实机测试，未确认其具体版本的原生技能导入规则。通用指令与脚本没有 Codex 专有执行依赖，但是否能完整自动闭环仍取决于客户端提供的工具和权限。

在新宿主上使用 [跨领域行为场景](behavior-scenarios.md) 试跑，并记录实际表现；不要只以“成功加载指令”判定整套闭环兼容。

## 能力降级

| 可用能力 | 可完成范围 |
| --- | --- |
| 只能对话或读取上传资料 | 诊断、计划；不足之处列出待补证据 |
| 可读取与编辑本地项目 | 诊断和经确认的修复；执行验证仍需工具 |
| 可执行命令并查看输出 | 非视觉项目的完整验证闭环 |
| 另可查看截图/页面 | 视觉任务的前后审阅 |
| 有 Python 3.9+ | 可选运行 evidence_gate.py，核对版本与证据绑定 |

若不使用 Python 检查器，保留同样的事实、证据与确认记录，并使用项目门禁。不得把“人工核对过版本”描述成“脚本已通过”。
