# 闭环诊断与修复

把用户报告的问题推进到有证据的候选交付。先判断问题归属，再决定是否修改；自动验证通过只表示候选就绪，不代表用户验收或部署完成。

## 接入项目

先读取项目适用的 AGENTS.md 和已有维护技能。已有项目规则、验证器和授权边界优先沿用，不替换成此框架的默认值。读取用户指定的项目配置；没有配置时，按 [项目接入](references/project-adapter.md) 识别输入、处理链、产物和验证方法。只补足本次任务需要的事实，不要求先建设完整工程体系。

在任务的工作目录保存简洁状态；格式和证据字段见 [任务记录](references/task-record.md)。项目不支持通用检查脚本时，可用已有门禁，明确记录适配方式。不要复制客户数据到个人技能仓库。

## 1. 定位与归因

从现象反向追踪：产物位置 → 实际生效的转换/程序/配置 → 原始输入。区分可观察事实、假设、参考依据和未确定部分。

- `data`：输入缺失、错误或与可信要求不一致。记录实际值、期望值、位置、影响和反馈建议；默认交付数据问题报告，不修改样式/程序掩盖输入。只有用户另行授权数据修正时才进入相应修复。
- `implementation`：输入表达正确，但生效的渲染、程序或配置没有正确处理。给出具体文件/规则/调用链、触发条件、正常反例和影响面。
- `mixed`：数据和实现都存在问题。拆分证据与处理范围，不笼统归为样式问题。
- `undetermined`：缺证据或无法区分。说明缺什么、下一步如何查，不试错式修改来掩盖未知。

参考 PDF 或截图只是依据之一。输入与参考本身不一致时先报告，不凭外观补线、补字。没有数据处理层的项目不必硬造数据问题分类。

## 2. 方案与确认

展示：根因、拟改位置与机制、预期可观察效果、影响范围、验证方法和正常反例。尚未修改时，效果只能称为预期；示意图必须标明是示意，不伪造修复后截图。

实施前获得用户对具体方案的确认。已有确认在同一范围内持续有效；从对话引用真实原话，不重复询问、不编造。记录计划文本的哈希及确认引用。改变根因、扩大修改范围或改变主要修复机制时更新计划并重新对齐；不把局部实现调整都当作新授权。

## 3. 执行、验证、返工

修改前保存当前在用输入/源码基线和原始产物，保留已有未提交工作。隔离方式遵循项目规则，不强制所有项目创建 worktree。生成产物应从源头重建，不直接修改 PDF、FO 或编译结果冒充修复。

先明确项目必需检查与通过标准，再修改。验证要绑定实际候选和源码版本：

- 复现原问题，验证本次效果；检查至少一个相关正常反例或回归案例。
- 视觉问题：用可用工具渲染基线与候选，实际打开相关页面，以可比尺度检查截图、文字/内容完整性、布局及邻近区域。页面漂移时按语义定位，不机械使用相同页码。
- 非视觉问题：使用可观察输出、断言或测试，不强制截图。
- 使用项目已有的完整门禁；编译成功、图片差异小或文件存在不能替代正确性验证。

验证失败后，基于证据修正并重新生成受影响候选与报告。默认最多连续 3 轮修复验证；项目可配置。相同失败连续 2 次且没有新证据时停止盲重试，汇报已知原因与需要的决定。范围变化遵守方案确认边界。`ERROR` 不算通过，`MANUAL_REVIEW` 不算自动验收成功。

使用通用证据检查器时，按 [门禁用法](references/gate-usage.md) 操作。它验证版本绑定、清单和报告，不替你判断图片是否正确，也不会运行项目测试。已有门禁结论仍必须真实执行取得。

## 4. 交付与恢复

自动验证通过后，交付根因、改动、前后证据、实际检查结果及限制，状态为 `ready_for_human`。用户实际验收后才记 `accepted`；合入、推送、发布或部署遵循独立授权，不因 skill 被调用就获得权限。

数据问题报告交付为 `reported_data_issue`，不是“样式已修复”。需要用户判断为 `manual_review`，缺输入为 `blocked`，工具异常为 `error`。任务生命周期与单次检查的 PASS/FAIL 分开。

每轮结束或中断前，保存当前根因、确认方案、基线/候选路径与哈希、失败项和下一步。恢复时核对磁盘真实状态；源码、输入或候选变化使对应验证失效，重新生成受影响证据，不能仅更新哈希保留旧 PASS。仅当需要部署时，再核对当前部署基线，禁止整树覆盖其他任务成果。
