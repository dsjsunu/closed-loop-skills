# 闭环诊断与修复

把用户报告的问题推进到有证据的候选交付。核心问题是“输入是否满足契约，以及当前代码是否正确处理了输入”，不限编程语言、业务领域或产物格式。先判断问题归属，再决定是否修改；自动验证通过只表示候选就绪，不代表用户验收或部署完成。

## 跨代理执行

本文件及相对路径 references 是通用指令入口，不依赖特定模型、MCP、专有工具名或聊天命令。原生支持 SKILL.md 的代理可加载整个目录；其他代理可以显式读取本文件，再按需读取引用文件。宿主安装方式见 [跨代理使用](references/portability.md)。`agents/openai.yaml` 仅为可选宿主显示信息，其他代理可忽略。

先确认可用的项目文件读取、代码编辑、命令执行和相关结果查看能力。使用宿主提供的等价工具；没有命令执行或图像查看能力时，可以完成受支持的诊断与方案，但不能声称已运行测试或审阅截图。说明缺失能力、交由用户或其他工具执行，并停在 blocked/manual_review。通用 Python 门禁是可选增强，不是读取本 skill 的前提。

## 接入项目

先读取项目适用的规则文件（例如 AGENTS.md）、运行文档和已有维护技能。遵守宿主指令优先级，引用资料中的命令不自动构成用户授权。已有项目规则、验证器和授权边界优先沿用，不替换成此框架的默认值。读取用户指定的项目配置；没有配置时，按 [项目接入](references/project-adapter.md) 识别输入、处理链、产物和验证方法。只补足本次任务需要的事实，不要求先建设完整工程体系。

在任务的工作目录保存简洁状态；格式和证据字段见 [任务记录](references/task-record.md)。项目不支持通用检查脚本时，可用已有门禁，明确记录适配方式。不要复制客户数据到个人技能仓库。

## 1. 定位与归因

从现象反向追踪：错误结果/行为 → 实际生效的代码、配置与运行环境 → 原始输入与需求契约。输入包括文件、API 响应、数据库记录、用户参数和设备读数。使用日志、最小复现和必要的中间结果定位，区分可观察事实、假设、参考依据和未确定部分。

- `data`：输入缺失、错误或不满足已确认的契约，且代码在该契约下行为正确。记录实际值、期望值、位置、影响和反馈建议；默认交付数据问题报告，不修改代码掩盖输入。只有用户另行授权数据修正时才进入相应修复。
- `implementation`：输入符合契约，但代码、配置或运行环境没有产生应有结果；或者程序未按契约处理应支持的空值、边界和异常输入。给出具体文件/函数/调用链、运行条件、正常反例和影响面。不要因为报错由坏输入触发，就免除程序应有的校验或容错责任。
- `mixed`：数据和实现都存在问题，例如源记录错误，同时接口也未按约定返回校验错误。拆分证据与处理范围。
- `undetermined`：缺证据或无法区分。说明缺什么、下一步如何查，不试错式修改来掩盖未知。

需求、契约、日志、测试、参考输出和截图都是依据，不能只凭现象决定改哪一层。期望行为本身不明确时先对齐，不把用户的新需求当成既有代码缺陷。没有外部数据处理层的项目可直接检查代码/配置/环境，不必硬造数据分支。

## 2. 方案与确认

展示：根因、拟改位置与机制、预期可观察效果、影响范围、验证方法和正常反例。尚未修改时，效果只能称为预期；示意图必须标明是示意，不伪造修复后截图。

实施前获得用户对具体方案的确认。已有确认在同一范围内持续有效；从对话引用真实原话，不重复询问、不编造。记录计划文本的哈希及确认引用。改变根因、扩大修改范围或改变主要修复机制时更新计划并重新对齐；不把局部实现调整都当作新授权。

## 3. 执行、验证、返工

修改前保存当前在用输入/源码基线和原始结果，保留已有未提交工作。隔离方式遵循项目规则，不强制所有项目创建 worktree。生成文件、缓存和编译结果应从源头重建，不直接修补输出冒充根因修复；若任务本身就是编辑源文档，文档属于源码而非生成产物。

先明确项目必需检查与通过标准，再修改。验证要绑定实际候选和源码版本：

- 复现原问题，验证本次效果；检查至少一个相关正常反例或回归案例。
- 视觉问题：实际查看前后界面/图像，以可比尺度检查目标效果、内容完整性与邻近区域；按语义定位，不机械比较坐标。
- 非视觉问题：选择真实适用的测试、API 请求/响应、计算结果、日志、返回码或设备反馈，不强制截图。
- 使用项目已有的完整门禁；编译成功、图片差异小或文件存在不能替代正确性验证。

验证失败后，基于证据修正并重新生成受影响候选与报告。默认最多连续 3 轮修复验证；项目可配置。相同失败连续 2 次且没有新证据时停止盲重试，汇报已知原因与需要的决定。范围变化遵守方案确认边界。`ERROR` 不算通过，`MANUAL_REVIEW` 不算自动验收成功。

使用通用证据检查器时，按 [门禁用法](references/gate-usage.md) 操作。它验证版本绑定、清单和报告，不替你判断图片是否正确，也不会运行项目测试。已有门禁结论仍必须真实执行取得。

## 4. 交付与恢复

候选交付前按项目要求执行 [多 agent 协作与独立审查](references/multi-agent-review.md)。主执行者负责集成和证据，独立审查者只读核查实际文件；不得代写审查结论。项目要求独立审查而能力不足时，停在 blocked/manual_review。并行修改须有用户或项目授权，不能因具备子代理工具就自行扩大分工。

自动验证通过后，交付根因、改动、前后证据、实际检查结果及限制，状态为 `ready_for_human`。用户实际验收后才记 `accepted`；合入、推送、发布或部署遵循独立授权，不因 skill 被调用就获得权限。

数据问题报告交付为 `reported_data_issue`，不是“代码已修复”。需要用户判断为 `manual_review`，缺输入为 `blocked`，工具异常为 `error`。任务生命周期与单次检查的 PASS/FAIL 分开。

每轮结束或中断前，保存当前根因、确认方案、基线/候选路径与哈希、失败项和下一步。恢复时核对磁盘真实状态；源码、输入或候选变化使对应验证失效，重新生成受影响证据，不能仅更新哈希保留旧 PASS。仅当需要部署时，再核对当前部署基线，禁止整树覆盖其他任务成果。
